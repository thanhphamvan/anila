# Open-source benchmark specification

Status: proposed measurement and acceptance plan, reviewed against the local
source on 2026-10-27. This document contains **no new benchmark results** and
does not certify release readiness. Publication remains subject to
[`OPEN_SOURCE_PLAN.md`](../OPEN_SOURCE_PLAN.md), including license notices, private-data
review and deployment validation. Historical results in
[`README.md`](README.md) describe earlier builds, not this snapshot.

## Questions the measurements should answer

1. How quickly does input reach decoded output and then a visible terminal?
2. How much useful terminal output reaches the client per second, at what
   network, CPU and memory cost, without missing or duplicating bytes?
3. What survives a browser or service connection failure, and how long does
   recovery take with production timers?
4. How do the native Rust service and browser wasm decoder behave on modest
   hosts and physical phones, including sustained load and backgrounding?
5. Which measured gains come from compression, batching or replay, and which
   comparisons, if any, isolate implementation-language effects?

Use component, local-stack and deployed-stack results as separate categories.
The service, Worker and frontend use Rust, but the system also includes tmux,
the browser, xterm.js, Cloudflare's runtime and a C zstd encoder. A system
benchmark cannot attribute all its results to Rust.

## What exists today

The source, rather than older prose or result files, defines these capabilities.

| Tool or suite | Current measurement or assertion | Limits on interpretation |
| --- | --- | --- |
| `anila-bench synth` | Four deterministic JSONL workloads: ticker, colored build output, TUI redraw and pseudorandom bytes | Overwrites those four names in `bench/workloads`; does not recreate real interactive users |
| `anila-bench codecs` | Six codecs × four batch windows × two raw frame caps: 48 rows per workload; byte round trips, ratio, frame counts and native encode/decode timing | Single-pass timings; simulated framing; estimated wire bytes; includes experimental streaming codecs |
| `anila-bench net` | Three production codec choices × four network profiles; 50 echo samples, burst completion, downstream proxy bytes and recovery time | Native probe, debug service, local Worker, no browser render or TLS, insecure development authentication |
| `anila-bench phone-cpu` | Release frontend wasm decoder, production encoders, browser CPU throttle; decode ms/decimal MB, mean µs/piece and size-group p50/p95 | Headless Chromium, not a physical phone; verifies decoded lengths, not browser output byte equality; excludes rendering and networking |
| `bench`, `phone`, `proxy_latency`, `proxy_bandwidth`, `harness_proxy` tests | Codec/framing helpers, phone summary helpers and proxy behavior | Correctness checks, not performance reports |
| `functional`, `chaos`, `browser`, `watch` suites | Stack behavior, reconnect/reset paths, browser flows and watch/hibernation rules | Do not provide the complete statistical, resource or deployed-cost measurements specified below |

Important measurement boundaries:

- Offline codecs are `none`, `lz4`, `zstd3`, `zstd3_stream`,
  `deflate_stream`, `zstd3_prefix`. Only `none`, `deflate_stream` and
  `zstd_stream` are selectable by `net`; the last uses complete zstd frames
  with prefix history. Do not equate it with the experimental long zstd stream.
- Offline batch windows are 0/4/16/32 ms and caps are 8/32 KiB. The phone
  runner uses 8 ms/32 KiB framing and production codec implementations, but
  its offline `frame` helper does not reproduce the service coalescer's
  immediate send after a quiet period. Do not call it a full packetizer replay.
- The offline wire estimate adds 19 protocol + approximately 4 WebSocket +
  29 TLS bytes per piece. It is neither a packet capture nor a billable-byte
  counter. Raw caps do not guarantee compressed payload caps.
- Network echo ends at the probe's accumulated decoded marker, sampled by
  polling. The `seq 1 20000` burst includes create/attach time and may see a
  tmux final-screen snapshot. Call it **burst completion**, not verified
  20,000-line goodput. Proxy downstream bytes exclude TLS and TCP/IP.
- Network recovery ends after a resume counter increases and output grows;
  that growth can be replay. It does not alone establish losslessness or time
  to the next newly generated byte. Its 500 ms ping and 2,000 ms dead timeout
  differ from production's 10 s and 25 s values.
- `Service::start` builds and starts `target/debug/anila-service` even when
  `cargo run --release` launches the benchmark. The local Worker build command
  requests release, and pins `worker-build` 0.8.7.
  Record these facts; production resource claims require a release-service
  selection feature in the benchmark runner. `Service::start_bin` exists as
  a library API, not a `net` CLI option.
- Browser decode timing includes the JS-to-wasm call, input copy, decoder and
  output-length return. Reset/setup and fetch/base64 preparation are outside
  the bulk timer. The bulk loop runs at least three passes and 300 ms;
  per-piece browser clock quantization limits small-piece percentiles.

## Commands available now

Run from the workspace root in a disposable benchmark checkout, with a reviewed
corpus. The commands below use existing subcommands and flags. Distinct output
directories prevent same-day/same-commit result replacement. Change `r01` for
each independent repetition. No command here deploys a Worker.

Prerequisites are cached Rust dependencies, the wasm target, tmux, Node/npm,
Trunk and Chrome/Chromium/Edge for browser runs. Set `ANILA_BROWSER` to an
installed browser when discovery fails. The stack invokes Wrangler 4.148.0;
its build hook may install worker-build. `CARGO_NET_OFFLINE=true` controls
Cargo, not npm or every external tool. Prepare and record tool versions before
timing; do not include downloads or builds in steady-state measurements.

```sh
# Deterministic corpus; inspect existing workloads before overwriting them.
CARGO_NET_OFFLINE=true cargo run --locked --release -p anila-e2e --bin anila-bench -- synth

# Native codec experiment; existing recorded workloads are included too.
CARGO_NET_OFFLINE=true cargo run --locked --release -p anila-e2e --bin anila-bench -- codecs --workloads bench/workloads --out bench/results/public-r01/codecs

# Local stack smoke/comparison; the service is still debug as explained above.
CARGO_NET_OFFLINE=true cargo run --locked --release -p anila-e2e --bin anila-bench -- net --profiles lan,good4g,poor4g,train --codecs none,deflate_stream,zstd_stream --out bench/results/public-r01/net

# Actual release wasm decoder in Chromium, including an unthrottled control.
CARGO_NET_OFFLINE=true cargo run --locked --release -p anila-e2e --bin anila-bench -- phone-cpu --workloads bench/workloads --rates 1,4,6 --out bench/results/public-r01/wasm

# Helpers and protocol/proxy regression checks.
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --test bench --test phone --test proxy_latency --test proxy_bandwidth --test harness_proxy
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --lib net_arguments

# Stack correctness, with private harness tmux servers and disposable sessions.
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --test functional -- --nocapture
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --test chaos -- --nocapture
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --test browser -- --nocapture
CARGO_NET_OFFLINE=true cargo test --locked -p anila-e2e --test watch -- --nocapture
```

The browser suite also needs its frontend build prerequisites. The Worker
harness refuses a checkout containing `worker/.dev.vars`; use an isolated
checkout rather than moving live credentials. The recorder is available as
`anila-bench record NAME --cols 120 --rows 40 -- PROGRAM ARGS...`; it records
and echoes real PTY output. Use only public fixtures and disposable sessions.
Never record a private workspace, credentials, real sessions or proprietary
assistant output into the public corpus. Review raw bytes, including escape
sequences and base64-decoded content, before publication.

These commands have been checked against source, not executed for this plan.
No `--iterations`, `--service-bin`, `--json`, `--device`, memory benchmark or
production-deployment benchmark flag currently exists. The additions below
are proposed implementation work, not runnable commands.

## Workloads and controlled experiments

Freeze a corpus manifest with workload name, generator version, seed, duration,
chunk timestamps, total raw bytes, SHA-256, terminal dimensions and provenance.
Keep correctness assertions outside timed codec sections. Retain incompressible
and small-output cases even when they make compression look worse.

| Workload | Required schedule and sizes | What it tests |
| --- | --- | --- |
| Existing synthetic corpus | All four workloads, unchanged; 80×24 and 120×40 where applicable | Reproduces historical codec decisions |
| Interactive echo, proposed extension | At least 1,000 unique markers per cell, fixed 300 ms offered interval; include sparse single keys and 4 KiB paste boundaries | p50/p95/p99 input response, queueing and input flow control |
| Verified bulk, proposed | 1/16/64 MiB framed deterministic records, compressible and seeded random; attach before producer starts; sequence + offset + final digest | Application goodput, completeness and backpressure, without snapshot shortcuts |
| Build and TUI replay | Public fixture traces; ANSI cursor moves, UTF-8, 30/60 redraws per second, 80×24 and 120×40 | Rendering/decoding load and useful-screen latency |
| Mixed sessions, proposed | 1/4/8 channels per tab; 1/4/16 tabs per room; one bulk sender plus one interactive channel | Fairness, fan-out cost and latency under contention |
| Idle, proposed | No browser; browser connected but quiet; background tab; quiet service with multiple machines | Baseline CPU, memory, wakeups and room hibernation |
| Lifecycle soak, proposed | At least 60 minutes and 100 open/close/reconnect cycles; fixed offered load and fault seed | Leaked PTYs, sockets, buffers, browser memory and degraded tails |

For verified bulk, use a test producer and a raw-output sink with a completion
handshake after attachment. Validate transport offsets and exact PTY bytes;
terminal line discipline and tmux can transform source bytes, so a generator's
source digest alone is insufficient. Record the bytes emitted at the service
boundary and compare them with the client's deduplicated decoded stream.
Browser screen-content equivalence is an additional assertion, not a substitute.

Stay within the limits in [`proto/src/limits.rs`](../proto/src/limits.rs): at
review time, 16 tabs/room, 8 channels/tab, 512 KiB unacknowledged flow window,
4 MiB replay/channel and 600 s disconnected grace. Test limit rejection
separately from supported-load benchmarks. Do not infer room capacity from
independent-machine totals or assume all buffers are allocated eagerly.

## Network and reconnect matrix

The existing proxy shapes the browser leg only. Each direction of each TCP
connection has its own rate bucket; multiple connections do not share a link
capacity. Latency is a queued chunk's arrival deadline, allowing overlapping
propagation delays; this is still a TCP byte-stream approximation. Blackhole
holds bytes and backpressures, and is not packet loss.

| Existing profile | Added one-way delay | Rate each direction, decimal B/s | Scheduled blackout |
| --- | ---: | ---: | --- |
| `lan` | 0 ms | Unlimited | None |
| `good4g` | 25 ms | 2,500,000 | None |
| `poor4g` | 75 ms | 125,000 | None |
| `train` | 200 ms | 32,000 | 3 s every 30 s |

The train clock spans codecs; a short run can miss the scheduled outage, or
hit a different phase for each codec. The explicit five-second recovery probe
suspends scheduled faults. Current train comparisons are diagnostic: the
proposed runner must replay identical fault events relative to workload start
for every variant and preserve the actual event log.

Add an isolated Linux network-namespace/netem rig for packet-level tests;
do not change the operator's default interface. Pin and publish its scripts,
queue limits, seeds, MTU and qdisc configuration before using it for a claim.
Use three distinct conditions: browser leg shaped, service leg shaped, both
legs independently shaped. Add asymmetric links, jitter (0/20/50 ms), packet
loss (0/0.1/1%), and forced TCP disconnects; validate achieved RTT, rate and
loss with a separate calibration flow. Record link aggregate capacity and
queueing, not only configured values. These are controlled profiles, not
claims to reproduce every cellular network.

Reconnect cases must cover 1/5/30/120-second outages, repeated flaps,
browser offline/online, background/foreground, service-link breaks, and a
physical phone Wi-Fi/cellular switch. Test accelerated timers and production
timers in separate series. Also exercise service restart/epoch change,
retained-history misses and grace expiry as reset scenarios. Overflow/history
miss cases may need a deterministic state-machine fixture because normal flow
control can pause the producer before a buffer would overflow.

Record timestamps for fault start, link restoration, fault detection,
socket ready, accepted resume/reset, first replayed byte, first fresh byte
and caught-up sequence. Report both end-to-end outage duration and recovery
after restoration. Synchronize only when cross-machine timestamps are needed;
prefer one monotonic observer for elapsed durations and publish sync error.

Within the same epoch and retained history, require exact ordered output,
no duplicate displayed bytes, contiguous offsets and the protocol's input
deduplication behavior. Record accepted input IDs at the test sink, including
the ambiguous send/ack failure window. Do not promise application-side
exactly-once effects across service crashes. When continuity cannot be kept,
require an explicit, expected reset and successful new output rather than
reporting a silently truncated stream as a lossless resume.

## Metrics and instrumentation to add

| Layer | Metric and boundary | Measurement method |
| --- | --- | --- |
| Native codec and state machine | ns/op, encode/decode MiB/s, allocations/op, retained bytes; small frames through maximum caps | Release harness over production `proto::codec`, framing/control parsing, replay and channel actions; batch above timer resolution; empty-loop/copy control |
| Service process | CPU seconds, average cores used, peak/steady RSS, Linux PSS where available; cost per verified raw MiB and per active channel | PID-scoped OS counters at a fixed cadence, separate tmux/child/runner; allocator profiling in a separate instrumented series |
| End-to-end terminal | Input-to-decoded-output and input-to-render-complete p50/p95/p99/max; offered/accepted rate; timeouts | Marker sequence timestamps plus xterm render observation; render callback and next animation frame are proxies, not display scanout; use camera if claiming physical key-to-photon latency |
| Verified streaming | Raw bytes validated / interval, compressed payload bytes, protocol bytes, captured link bytes, compression ratio | Start at producer release after attach, stop at validated final byte; report startup separately and name numerator/denominator |
| Browser | Wasm decode CPU, JS/wasm crossing/copy cost, main-thread long tasks, missed-frame fraction, wasm memory high-water and renderer RSS | Existing decoder hook plus correctness hash, browser tracing and memory counters; fixed browser/version/viewport; no claim that wasm linear memory equals process RSS |
| Worker/room | Per-event and total CPU, wall time, cold/warm attach, concurrent sockets, duration/hibernation activity | Local runtime diagnostics separately from deployed telemetry; attribute deployment and runtime overhead explicitly |
| Assets/startup | Service binary size, wasm/JS/raw and served compressed bytes, first-load and cached time-to-usable-terminal | Release artifacts, clean profile vs warm cache, actual HTTP transfer sizes and service-worker state |
| Energy, optional | Joules/workload and idle power delta | Physical device power instrumentation with fixed screen/radio/battery conditions; CPU throttle alone supports no battery-life claim |

Process CPU percentage must state its convention: 100% equals one fully used
core; also report CPU seconds and wall time. RSS/PSS are platform-specific;
do not directly rank macOS footprint against Linux RSS. Keep the producer,
tmux, service, local Worker, browser and driver in separate accounting groups.
The probe accumulates output in memory; its growth must not be attributed to
the service. Never derive Cloudflare billing or hibernation savings from local
Wrangler wall time. A future authorized deployment needs its own dated usage
measurements and verified pricing assumptions.

## Hardware, devices and repeatability

Use at least one x86_64 Linux host and one ARM64 host, with model, cores,
RAM, OS/kernel, compiler and enabled CPU features recorded. Physical browser
checks should include a modest Android phone with Chrome and an iPhone with
Safari, plus desktop Chromium. Record exact device/OS/browser versions,
viewport, refresh rate, battery/power mode, thermals, connection and whether
the tab is visible. Desktop 4×/6× CDP throttling is a reproducible stress test,
not evidence for a named phone or Safari.

For each result bundle, preserve full commit identity or, for this initially
uncommitted snapshot, a source-tree hash and dirty-state manifest. A short Git
label alone is insufficient. Include Cargo.lock hash, workload hashes,
`rustc -Vv`, Cargo/Trunk/wasm-bindgen/worker-build/Wrangler/browser/tmux
versions, target triple, build profile, features, RUSTFLAGS, codec settings,
runtime timers, topology, authentication mode and execution command. The
`stable` toolchain channel is movable; preserve the resolved compiler version.
Record release LTO/codegen settings and wasm `opt-level = "z"`. Compare any
speed-optimized wasm variant as a separate size/speed tradeoff.

Run one untimed warm-up per component/variant, then at least ten independent
timed repetitions of each primary cell. Randomize variant order with a
recorded seed, or use balanced AB/BA blocks. Keep identical workload/fault
schedules, process placement and power policy. Report cold and warm startup
separately; include a second-host or second-day replication for headline claims.

Store raw latency samples and per-run metrics. Publish per-run distributions,
median and interquartile range across runs, and paired 95% bootstrap confidence
intervals for comparison ratios. Resample independent runs or blocks, not
thousands of correlated frames as if each were an independent experiment.
Use at least 1,000 samples per cell before a p99 claim and label it exploratory
if the tail confidence interval is broad. Never average p95 values and call
that the combined p95. Retain failed/time-out runs and their deadlines; do not
drop them from success-rate denominators or invent completion times for them.

## Fair comparisons and claims

The primary baseline is the same commit with `none`, then `deflate_stream`
and `zstd_stream`, with identical frame policy, load, network, timers and
correctness. Compare a prior release to a candidate only after preserving
their source/build manifests and matching behavior. Batching variants and
default changes currently need a controlled implementation patch; record it.

For comparisons with SSH, another browser terminal or a non-Rust prototype,
match host, path, relay placement, TLS/authentication, terminal dimensions,
compression, reconnect guarantees, rendering library and concurrency where
possible. Publish unmatched features next to the result. Direct SSH without
a relay is useful user context but cannot isolate language effects.

A language-specific experiment needs equivalent algorithms and protocol,
matched libraries/backends, release builds, feature parity and independently
reviewed idiomatic implementations. A C zstd versus pure-Rust deflate result
compares codecs and implementations simultaneously. Rust-native versus Rust-wasm
compares execution targets; neither establishes Rust superiority over another
language. Present CPU, memory, wire bytes, startup and complexity tradeoffs,
including regressions. A valid headline names its workload, environment and
baseline: “X% lower measured service CPU for this workload than version Y.”
Do not publish “Rust is faster,” “zero overhead,” “battery efficient,” or
“lossless under every failure” based on this suite.

## Acceptance criteria and delivery order

These are proposed gates for adopting this plan, not observed passes or an
existing product SLA. Freeze them before running a candidate comparison.

1. **Trustworthy harness first.** Add explicit release-service selection and
   artifact verification, unique run IDs/manifests, raw samples, deterministic
   fault schedules and production-timer variants. Add regression tests for
   these changes. Preserve legacy measurements under their actual labels.
2. **Correctness is mandatory.** Every timed codec must pass exact round trips;
   wasm must verify bytes or a collision-resistant digest, not lengths alone.
   Verified streams must pass sequence/digest checks for every completed run.
   All expected resume/reset cases must be classified correctly, with no
   unexplained stream gaps, duplicate application input IDs, crashes or leaked
   live PTYs/sockets after the lifecycle soak. Record timeouts as failures.
3. **Release evidence.** Run existing unit/contract, benchmark-helper and
   relevant stack suites on the final authentication behavior. A DEV_INSECURE
   benchmark is insufficient evidence for authenticated attach/startup.
   Add physical-device correctness and rendering runs before mobile UX claims.
4. **Performance regression gate.** Against a frozen, same-machine release
   baseline, investigate a >10% slowdown in median goodput or >10% increase in
   CPU/raw MiB, steady-state memory, or p95 latency (for latency, also require
   >5 ms absolute increase). Reject an unexplained regression when the paired
   95% interval lies entirely beyond that threshold; an interval crossing it
   is inconclusive and requires more runs, not a pass. Exclude fault-inclusive
   latency from ordinary-echo gates and assess it against identical faults.
5. **Bounded resources.** Define a per-platform idle and per-channel memory
   budget from a clean baseline before candidate runs. Logical retained buffers
   must obey protocol limits throughout. For the soak, compare equal-load
   windows after warm-up and cleanup; a sustained >10% footprint increase or
   persistent handle/PTY growth requires investigation. RSS need not return
   immediately to initial levels because allocators retain memory.
6. **Recovery targets.** Require every in-contract deterministic recovery case
   to complete within its predeclared deadline. Derive that deadline from the
   configured dead timer, maximum reconnect backoff, shaped-path handshake and
   backlog-drain allowance; store the numeric deadline per case before testing.
   Production timers must not be judged against the accelerated runner's
   recovery numbers. Reset cases must become usable within their own deadline.
7. **Publication package.** Provide raw results, manifests, scripts, hashes,
   failure logs scrubbed of secrets, confidence intervals and a short report
   with topology and limitations. Missing release/physical-device/deployed
   measurements must be marked “not measured.” Only publish claims supported
   by reproducible measurements of the final public candidate.

Implement in that order: trustworthy harness and byte correctness, native and
wasm component measurements, local release-stack resources and fault matrix,
physical devices, then a separately authorized deployed validation. The
existing commands can establish a diagnostic baseline immediately; the wider
performance and Rust claims require the proposed instrumentation and evidence.
